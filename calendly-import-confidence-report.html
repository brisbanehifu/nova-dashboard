Diagnosis

  • Root cause confirmed: The original Calendly import dropped the Event UUID. 1,983 of 2,022 imported bookings have external_id = NULL. Without that, neither the migration script nor the BAT reschedule UI can know whether a Calendly event already exists in BAT — every reschedule looks "new" to the system. This is exactly what the locked migration playbook (PR #2 in the queue: "external_id REQUIRED — compute hash if missing") was designed to fix.
  • Reschedule signal is missing from the fresh CSV: Calendly's "Active only" export filter strips out canceled events. So a reschedule appears in the CSV as two active rows for the same invitee — no Cancellation reason: Rescheduled flag, no link between them. We'd need a Calendly export with cancellations included to programmatically dedupe.
  • No exact-match dupes: 0 cases of (email + service + date + time) appearing twice. So the import worked at the row level — it's the reschedule case that's untracked, not raw duplication.
  • Most "same-customer ≤14 day" pairs look legit: Of the 53 candidate pairs, 21 are internal clinic emails (brisbane.hifu.clinic@gmail.com, hello@brisbanehifu.com, luci.hifu@gmail.com, mskimklein@gmail.com) — admin testing or staff comp bookings, not customer dupes. Of the 32 customer pairs, most are 7-14 days apart with two completed statuses — these look like clients who came in, then booked again two weeks later (HIFU follow-up cadence). The same-day pairs (8) and the (confirmed + cancelled) pair on 2026-05-07 are the suspicious ones worth manual review.
