Quoting an estimate as fact, then quoting a different number later without flagging the gap, was the "misreporting and half-checked things" Kim called out.

Full rule banked: memory/feedback_verify_before_reporting.md — next session reads this BEFORE doing any analysis work.

📜 The protocol — for the next session, before anything else

Before reporting ANY number / behaviour / "X is working" claim:

  1. State what underlying source backs the claim. e.g. "notification_logs table" not "the cron logged it." e.g. "Kim's Stripe dashboard at brisbane.hifu.clinic@gmail.com" not "stripe_payments table."
  2. If the source is a counter, log line, or information_schema estimate — say so. Those are proxies, not facts. Label them UNVERIFIED.
  3. If two queries give different numbers, reconcile them before reporting OR flag the gap explicitly. Never let an inconsistent pair ride.
  4. When Kim's under fire, "I don't know yet, let me check" is the right answer. 30 seconds of "let me verify" protects hours of trust-rebuild.
  5. Don't compress a contradictory state into a single positive sentence. "Stripe is working" hid that there's a public-booking skip-deposit bypass + the Connect path is null + Kim's dashboard hasn't been checked.
