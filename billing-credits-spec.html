1. The problem in one paragraph

Today, every tenant on the platform is assumed to be paying. Brisbane HIFU is shown as Multi $79 AUD/mo on its billing page, but Kim has been clear it doesn't actually pay — the record is fictional. There's no way to mark a tenant as comped, no audit trail, no impact on Stripe, and no impact on investor MRR reporting. Future comps (beta partners, AppSumo lifetime, demo accounts, Kim's other businesses) will hit the same wall.

Kim's ask, 7 May 2026: "I want to be able to apply a credit to clients who do not have to pay. This is currently not in our billing. But in terms of Brisbane HIFU they are one of those clients. So can you write the spec up for how we manage that."

2. Data model — credit ledger (locked)

Two new tables. No fields added to tenants — clean ledger pattern, full audit trail, supports partial credits and expiries.

TablePurposeKey columns
tenant_credits Source-of-truth ledger. One row per credit ever granted. credit_type (PERCENT/AMOUNT) · credit_value · duration_type (LIFETIME/UNTIL_DATE/N_INVOICES) · expires_at · invoices_total / invoices_consumed · reason · reason_category · granted_by / granted_at · revoked_* set
tenant_credit_applications Audit trail of credits applied to specific Stripe invoices. credit_id → tenant_credits · stripe_invoice_id · amount_credited · currency · applied_at

3. End-to-end flow — three actors

👑 Super-admin (Kim)

  1. Open /super-admin/tenants
  2. Find Brisbane HIFU row → click "Manage credits"
  3. Modal: pick type/value/duration/reason
  4. Grant → POST /api/super-admin/tenants/:id/credits
  5. Server inserts ledger row + audit log + syncs Stripe sub pause_collection
  6. Tenant row now shows teal "Comped" pill

🏢 Tenant admin (BH)

  1. Open /admin/settings/billing
  2. GET /api/billing/me returns extended payload with active_credits[] + next_invoice_total: 0
  3. UI shows green credit pill: "💚 100% credit applied — Founding Clinic"
  4. Next-bill amount displays as $0.00 USD

💸 Stripe webhook

  1. invoice.upcoming fires for BH
  2. Handler calls applyCreditsToStripeInvoice(tenantId, invoiceId)
  3. For 100% credit: void invoice via Stripe API
  4. For partial: add negative line item
  5. Insert tenant_credit_applications row
  6. Increment consumed counter for finite credits

📊 Investor / MRR view

  1. GET /api/super-admin/metrics/mrr returns 3 numbers:
  2. gross_mrr — sum of all plan prices
  3. net_mrr — gross minus active credit value at MRR weight
  4. comp_count — tenants with active 100% credit
  5. Dashboard tile shows all three; comp list expandable below

8. Why this matters

  • Investor metrics integrity — MRR is overstated today because BH is counted as paying. The gross/net/comp split fixes this.
  • Stripe state honesty — BH's Stripe sub is currently in an unknown state (likely no active sub, or quietly failing payments). The grant flow puts it in a clean pause_collection state.
  • Future scaling — every comp Kim wants to grant (beta partners, AppSumo lifetime, demo tenants) needs this exact plumbing. Building it once.
  • Audit story — financial records currently don't match reality. Ledger + applications table = clean trail for any dispute.
