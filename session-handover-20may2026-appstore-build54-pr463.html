Hard-delete semantics — why we're not cascading clinic data

Apple's wording on 5.1.1(v) is "give users more control of the data they've shared." That's the USER's data — not their clients' data. The hard-delete in PR #463 is scoped accordingly:

  • Cascaded automatically: the user's own admin_users row + their biometric_enrollments + their password_reset_tokens via existing FK_abe_user / FK_pd_user ON DELETE CASCADE constraints.
  • NOT cascaded: bookings, contacts, services, payments etc. They reference tenants via ON DELETE RESTRICT because they represent clients' data (appointments, health notes, payment receipts) with independent retention obligations under health-record and tax law.
  • Tenant closure: when the deleted user was the last active owner, tenants.status flips to 'closed' and name to "Closed account #<id>". Staff can no longer sign in and the public booking page returns 404. No new records are created against a closed tenant.

Option α (hard-delete + type-DELETE confirm) was chosen over Option β (30-day soft-delete grace) because Kim explicitly asked for the fastest Apple-compliant path off the rejection treadmill, and BAT's clinic owners are technical enough that an accidental delete-with-typing-confirmation is essentially impossible. Soft-delete with grace is a future-proofing enhancement; can be retrofitted later.
