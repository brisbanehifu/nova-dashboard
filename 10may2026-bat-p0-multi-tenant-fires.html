Issue detail (today's session)

P0

1. Stripe Connect — public booking deposits broken

PR #392 LIVE
BH impact: No client could pay a deposit on a service that required one. Browser console showed No such payment_intent: pi_3TV6n…. Multiple texts to Kim from confused clients.

Root cause: Backend routes payment intents directly to BH's connected Stripe sub-account via { stripeAccount }. Frontend initialised Stripe.js with plain loadStripe(publishableKey) — no stripeAccount option — so JS asked the platform account for an intent that lives on the sub-account. The Jose chat path always handled this correctly; the public BookingPage simply hadn't been updated when Connect was enabled.

Interim (PR #392 LIVE): public booking page bypasses online deposit entirely. Clients book → confirmation → pay at clinic. Slot still held (status=tentative). Reverting is a one-line restore.

Proper fix (PR #391 parked): backend returns stripeAccount; frontend caches loadStripe per (key, account); reducer threads stripeAccount through BookingFlowState. Re-enable when verified end-to-end on PROD.

Files: index.js (response shape) · frontend/src/lib/api.ts (return type) · frontend/src/types/index.ts (state) · frontend/src/pages/booking/BookingPage.tsx (cache + reducer + Elements mount)

P0

2. Booking durations wrong → calendar blocking wrong time

PR #396 in CI
BH impact: 30-min appointments rendered as 60-min on the calendar. Time slots looked unavailable. Clients told Kim they couldn't book; opportunities lost. Same wrong duration also went to clients via SMS confirmation.

Root cause: PR #385 fixed CREATE-time so new bookings get the canonical duration from event_types. But existing PROD rows still carry stale duration snapshots from before that shipped — and the UI reads those snapshots directly for display + calendar block height.

PR #396: server-side normalisation at READ time. getAllBookings + getBookingById JOIN event_types and override duration + recompute end_time from canonical service config before returning. DB rows untouched (no risky mass-backfill — some non-canonical durations may be intentional), but every consumer (slideout, calendar, mobile, exports) sees correct values instantly.
P0

3. Contact save silent-failure

PR #395 in CI
BH impact: Kim added Emma Martin via the desktop admin. Form looked like it saved (exited edit mode, no error). She wasn't in the contact list. Booking made for her also went missing. No SMS / email workflow fired because contact + booking both failed silently.

Root cause: handleSave in ContactRecordPage.tsx ran setEditing(false) regardless of HTTP status. console.error only fires on network errors — 4xx/5xx don't throw on fetch, they resolve. So no toast, no console error, no failed-state UI. Just a phantom save.

Check res.ok before parsing. Throw on non-2xx with the server's message body. Throw if 201 came back without an id field. setEditing(false) ONLY on confirmed success. Surface failures via window.alert() — unmissable. Same shape applied to the PUT branch.

What this fix doesn't do: the original Emma Martin save 4xx/5xx'd for an unknown reason. With this in place, the next attempt will surface the actual error so we can diagnose root cause instead of chasing a phantom.

P0

4. Multi-tenant data leak — Redlands name with BH services + contacts

PR #397 in CI
BH impact: When Kim signed Redlands up in another browser tab, the same browser's BH JWT in localStorage created split-brain UI. Routes using JWT correctly returned Redlands data; routes using host-resolution returned BH data. Tenant isolation breached visually for ~hours before noticed.

Root cause: 205 occurrences of req.tenantId || 1 across 25 backend files. The host resolver on app.bookatreatment.ai returns UNRESOLVED → defaults to tenant 1 (BH). PR #347 fixed 13 high-priority files; the other 25 stayed as-is and silently rotted into this exact bug at first second-tenant.

Mechanical sweep: req.tenantId || 1 → req.user?.tenantId || req.tenantId || 1. Same fallback chain, just JWT first. node -c passes. Same shape PR #347 used.

Files: index.js (102) · marketing.js (24) · pos.js (24) · subscriptions.js (7) · meta-ads.js (5) · locations.js (5) · 4 OAuth files (14) · 14 single-occurrence files.
P0

5. Redlands owner locked out of login

PR #398 in CI
BH impact: Indirect — but every future trial signup would hit the same wall. The canonical login URL app.bookatreatment.ai/admin/login host-resolves to tenant 1 (BH); the login lookup is tenant-scoped → no match for the new tenant's email → "Invalid username or password" with correct credentials.

Root cause: auth.js login() had a cross-tenant fallback added in PR #381, but only for the App Store reviewer demo user (gated on a hardcoded username). PR #397 didn't help because login has no JWT yet (user not signed in).

Generalise the cross-tenant fallback. When no match in the host-resolved tenant, search globally by email + is_active=1, take the most recently active match. bcrypt.compare still validates password (wrong creds still fail). Logged when fallback fires so unexpected bleed-through is auditable.
Once #398 deploys: Redlands owner logs in at app.bookatreatment.ai/admin/login → JWT minted with tenantId=2 → Redlands data only.

Standing rules locked today

  1. JWT-first everywhere on authenticated backend routes. Canonical pattern: req.user?.tenantId || req.tenantId || 1. Never bare req.tenantId || 1.
  2. Login does cross-tenant lookup when host-resolved tenant has no email match. bcrypt still validates password.
  3. Don't mix tenants in the same browser profile. One browser/profile per tenant or use incognito for the second one. localStorage auth_token is shared across tabs.
  4. Email uniqueness across tenants at register() — TBD, hardening backlog. The cross-tenant login fallback picks most-recently-active match when collisions exist.

Hardening backlog — order of priority

  1. Email uniqueness enforcement at signup time.
  2. Per-tenant subdomains (redlands.bookatreatment.ai) → host resolver always wins → fewer cross-tenant fallbacks needed.
  3. ESLint rule banning bare req.tenantId || 1 patterns. Lint-block on PR.
  4. Integration test in CI: sign up a fresh tenant and assert (a) login works, (b) data isolation between two simulated tenants.
  5. Re-enable online deposit on public booking page once PR #391 (Stripe Connect proper fix) is verified end-to-end.
  6. Fix the unpaid-deposit-cron nl.tenant_id SQL error so auto-reminders resume.
