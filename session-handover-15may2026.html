🔴 P0 #2 banked — cross-tenant data leak on /api/contacts (FIX IN FLIGHT)

Status: 🟣 PR #460 OPEN · CI RUNNING · awaiting Kim's merge go-ahead per Tier-3 Mode A.

One-line summary: UAT plan §4.4 against demo.bookatreatment.ai with a tenant-3 JWT returned 47 of tenant 1's contacts × 3 consecutive calls. Root cause: 5 CRUD handlers in index.js called contacts.js helpers without passing tenantId → helpers defaulted to tenantId=1. The PR #347 / PR #397 multi-tenant sweep missed contacts entirely.

Affected surface (5 handlers)

  • POST /api/contacts
  • GET /api/contacts
  • GET /api/contacts/:id
  • PUT /api/contacts/:id
  • DELETE /api/contacts/:id

Pre-fix real-world impact on PROD

  • Tenant 1 (Brisbane HIFU) — unaffected. Default-1 fallback matched the actual tenant, so reads/writes stayed correct.
  • Tenant 4 (Redlands HIFU / Grace) — latent breach. The moment Grace opened the Clients page she would have seen Brisbane HIFU's full client list: names, emails, phones, age, notes, allergies. Not yet triggered because Grace is PARKED (per the Redlands snooze decisions banked earlier today).
  • Every future non-tenant-1 customer — same breach class, same trigger.

Fix shape

Canonical resolution at the top of each handler:

const tenantId = req.user?.tenantId || req.tenantId || 1;

...then threaded through each contacts.js helper call. Unique grep marker contacts-crud-tenant-scoping-15may2026 appears 5× in index.js — use it to verify the deployed bundle contains the fix. Shipped via PR #460.

Why this is a protocol WIN (like the Stripe P0)

UAT §4.4 was authored as a multi-tenant safety net. The FIRST time it ran end-to-end against demo.bookatreatment.ai, it caught a real breach class before any non-tenant-1 customer onboarded. Same energy as the Stripe regression catch below: discipline (writing + actually running the safety net) caught the failure before any real customer hit it.
